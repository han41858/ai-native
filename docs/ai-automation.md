# AI 개발 자동화 지침

이 문서는 GitHub Issue 기반 개발 → 독립 리뷰 → CI → 머지 → Issue 종료 자동화를 도입하거나 개선할 때 적용합니다. 특정 언어, 프레임워크 또는 자동화 엔진의 사용을 강제하지 않습니다.

## 1. 적용 원칙

- 프로젝트의 규모, 기술 스택, 운영 환경 및 자동화 범위에 따라 필요한 요구사항을 선택하여 적용합니다.
- 보안, 권한, 작업 무결성 및 머지 안전성에 관한 요구사항은 적용 대상 기능에서 반드시 준수합니다. 프로젝트 규모나 운영 비용을 이유로 이러한 보호 조건을 생략하지 않습니다.
- 사용하지 않는 기능이나 해당하지 않는 환경에 관한 요구사항은 적용하지 않아도 됩니다. 해당 기능을 사용하는 경우에는 관련 안전 조건을 충족합니다.
- 권장 기능과 기본값은 구현 복잡도, 운영 비용 및 기대 효과를 고려하여 적용 여부와 설정값을 조정할 수 있습니다. 자동 복구, 병렬 실행, 캐시 등의 기능을 지침 충족만을 목적으로 추가하지 않습니다.
- 적용하지 않은 요구사항은 이유를 명시합니다. 미구현 상태나 검증되지 않은 상태를 충족으로 판단하지 않습니다.
- 기존 구현과 먼저 비교하고 이미 충족하는 항목은 변경하지 않습니다. 프로젝트의 브랜치·권한·배포·검사 정책을 보존하며 적용 불가 항목과 이유를 기록합니다.
- 결정적으로 처리 가능한 작업은 코드로 강제하고 모델은 요구사항 이해, 개발, 리뷰, 복구에 필요한 판단을 담당합니다.
- 자동화 실행 승인은 사용자에게 위임받은 범위의 작업 권한입니다. 개발 라벨과 자동 머지 승인 범위를 명확히 정의하며, 단순 Issue 등록만으로 자동 머지를 허용하지 않습니다.
- 현재 작업 저장소 외에는 읽기 참고만 허용합니다. 공통 지침의 개선 필요성을 보고하되 다른 저장소를 임의로 수정하지 않습니다.
- [도입 및 검증 체크리스트](ai-automation-checklist.md)를 함께 사용합니다.

## 2. 실행 흐름 및 상태

전체 자동화를 도입하는 경우의 기본 흐름: 실행 승인 → 사전 검사 및 의존성 확인 → 기준 스냅샷 확보 → 개발 → 편집 적용 및 격리 검증 → Draft PR 생성·갱신 → 독립 리뷰 → 필수 CI → 승인된 대상 브랜치 머지 → Issue 완료 확인. 일부 단계만 자동화하는 프로젝트는 해당 범위의 요구사항과 기존 수동 승인·검증 절차를 유지합니다.

- 개발자와 리뷰어를 분리합니다. 기본은 Codex 개발, Claude 리뷰이며 공급자와 모델은 설정으로 변경할 수 있습니다. 개발자 변경 시 리뷰어도 독립적으로 선택합니다.
- 실행 시작 전과 모델 호출·브랜치 갱신·게시·머지 등 주요 경계에서 Issue가 열려 있는지, 승인 라벨·중단 라벨, 대상 저장소, 작업 브랜치, 기준과 HEAD, 수동 변경 여부를 확인합니다.
- Issue 본문이나 승인 범위가 변경되면 기존 결과를 무조건 재사용하지 않습니다. 변경 의도와 새 승인 여부를 검증합니다.
- 단계별 상태를 내구성 있는 저장소에 기록하며 재실행 시 실제 GitHub 상태와 대조합니다. 모델 응답만으로 외부 작업 성공을 판정하지 않습니다.
- 같은 Issue의 중복 실행, 중복 이벤트 및 예약 소비를 방지합니다. 서로 다른 Issue의 병렬 실행을 지원하는 경우 기준 변경 및 머지 경쟁을 안전하게 처리합니다.
- 선행 작업이 지정된 경우 모든 선행 PR이 의도한 대상 브랜치에 실제 머지됐는지 검증합니다. 단순 종료나 큐 순서만으로 완료로 간주하지 않습니다. 대기 중인 후속 작업은 선행 완료 이벤트에서 승인·중단 조건을 재검사하여 중복 없이 재개합니다.

### 상태 규격

프로젝트별 상태명을 유지할 수 있으나 다음 의미를 구별하고 외부 관측 도구가 해석할 수 있도록 대응 관계를 문서화합니다.

| 권장 상태 | 의미 |
| --- | --- |
| queued | 실행 대기 |
| waiting_dependency | 선행 작업 대기 |
| developing | 개발 및 검증 중 |
| reviewing | 독립 리뷰 중 |
| waiting_ci | 현재 HEAD의 CI 대기 |
| ci_failed | 현재 HEAD의 필수 CI 실패 |
| repairing_ci | CI 실패 보완 중 |
| recovering_base | 기준 브랜치 변경 복구 중 |
| needs_human | 사람의 판단 또는 조치 필요 |
| failed | 자동화 자체 오류 |
| stopped | 명시적으로 중단됨 |
| merged | PR 머지 완료, Issue 종료 미확인 |
| completed | 머지 및 Issue 완료 확인 |

대기 상태는 자동화 실패로 처리하지 않습니다. 복구 중인 CI 실패를 최종 실패처럼 표시하지 않으며, 사람 확인이 필요한 상태가 단순 CI 성공 이벤트로 해제되지 않도록 합니다.

## 3. 모델 실행과 탐색

- 개발과 리뷰의 호출 예산을 독립적으로 관리합니다. 호출 횟수·출력 토큰·요청 시간·무응답 시간·전체 작업 시간·전체 복구 비용에 상한을 둡니다. 재진입이나 HEAD 갱신으로 전체 상한이 무제한 초기화되지 않도록 합니다.
- 권장 초기값은 개발 40턴, 리뷰 40~45턴, 결과 형식 교정 1회입니다. 출력 토큰, 추론 수준, 요청·전체 시간은 공급자 지원 범위와 실측에 맞게 조정합니다.
- 탐색 도구는 파일 목록, 파일 부분 읽기, 문구·심볼 검색을 지원합니다. 관련 테스트와 문서도 읽을 수 있어야 합니다. 도구 요청이 한도를 넘으면 허용 범위의 결과와 나머지 미실행 사유를 반환하고, 확보한 근거로 결과를 제출하도록 합니다.
- 최종 구조화 결과 제출과 필요 시 교정에 사용할 호출 예산을 미리 확보합니다. 마지막 탐색 이후 결과를 제출할 수 없는 구조를 만들지 않습니다.
- 대용량 응답은 공급자가 지원하는 스트리밍을 사용하고 이벤트 조립, 다중 도구 호출, 연결 실패, 무응답·전체 시간 초과, 완료 이벤트 누락, 출력 한도 도달을 구분합니다. 중단 시 reader와 요청을 정리합니다.
- Claude의 서명된 thinking 및 비공개 블록은 원문과 순서를 보존합니다. 같은 대화의 시스템 지침, 기존 메시지와 도구 정의를 변경하지 않습니다. 턴 안내는 새 메시지에만 넣고 마지막 호출에는 지원되는 방식으로 도구 선택을 제한합니다. 빈 텍스트와 빈 도구 결과는 공급자 형식에 맞게 처리합니다.
- HTTP 400 등 요청 오류, 인증·권한 오류, 일시적 제한·서버 오류를 구분합니다. 영구 오류는 무조건 재시도하지 않으며, 응답 유실로 실제 실행 여부가 불확실하면 중복 호출·게시를 방지합니다.
- 공급자 SDK 또는 자체 어댑터를 사용할 수 있으나 실제 사용하는 버전의 공식 계약과 회귀 테스트를 기준으로 검증합니다.

## 4. 구조화 결과와 코드 편집

- 개발 결과는 완료, 진행 중(in_progress), 사람 확인 필요(needs_human)를 구별합니다. 미완성 작업은 남은 예산 안에서 같은 대화로 이어가고 부분 수정안을 게시하지 않습니다.
- 스키마와 실제 검증 제약을 일치시킵니다. 요약 길이, 편집·지적 개수, 필수 필드, 상태별 조건 등 위반 사유를 모델에 구체적으로 제공하고 남은 예산 내에서 교정합니다.
- 사람 확인 요청은 존중합니다. 중단 사유가 비어 있거나 진행 메시지뿐이면 설명만 제한적으로 요청하고 중단 결정을 승인으로 바꾸지 않습니다.
- 편집은 기준 스냅샷에 대해 검증합니다. 원문 교체 방식이면 정확히 한 곳에서 일치해야 하며, 누락·중복 일치는 파일과 편집 순번·사유를 알려 같은 스냅샷에서 전체 수정안을 다시 검증합니다. 유사 문자열 임의 교체나 부분 적용·게시를 금지합니다.
- 경로 순회, 심볼릭 링크 탈출, 비밀 파일, Git 내부 데이터, 설치 결과물 및 보호 경로 등은 차단합니다. 권한·경로 위반을 형식 교정으로 우회하지 않습니다.
- 필요한 관련 테스트·문서·설정 파일을 편집할 수 있도록 범위를 구성합니다. 파일 크기·페이지 조회 한도는 실제 저장소 파일과 잠금 파일을 고려합니다. 워크플로와 자동화 자체 변경은 별도 보안·승인 정책을 적용합니다.
- 커밋·PR 제목은 프로젝트 규칙에 따라 코드로 검증합니다. 모델 제목이 부적합하면 검증된 Issue 제목을 사용할 수 있으며 둘 다 부적합하면 교정하거나 중단합니다.

## 5. 게시 전 검증

- 삭제하지 않은 변경 파일에 프로젝트의 고정된 포매터와 설정을 적용합니다. 포맷만 다른 변경을 모델에 다시 요청하지 않습니다. Rust 등 별도 언어의 포맷 정책도 적용합니다.
- 포맷 결과의 파일 목록과 경로·파일 유형을 검증하고 원래 허용 범위 밖의 변경을 거부합니다. 검증한 최종 내용만 커밋합니다.
- 후보 코드 실행은 모델·게시 자격 증명이 없는 격리 환경에서 수행합니다. 검증에 불필요한 네트워크 접근, 호스트 쓰기와 권한을 제한합니다. 신뢰된 기준의 검증 절차를 후보 코드가 임의로 약화하지 못하게 합니다.
- 의존성 준비는 잠금 파일과 고정 도구를 사용하며 설치 스크립트·외부 접근의 위험을 검토합니다. 의존성 캐시는 신뢰 경계를 구분하고 후보 코드로 오염시키지 않습니다.
- 변경 영향에 따라 포맷·타입 검사·단위·통합·브라우저·빌드 검사를 수행합니다. 문서 전용 변경은 관련 검사만 수행할 수 있으나 불확실하거나 혼합된 변경은 보수적으로 검사합니다. 필수 CI 결과 보고와 브랜치 보호는 유지합니다.
- 화면 변경 시 기존 UI 테스트의 실제 내용을 개발 및 리뷰에서 확인하고 필요한 테스트를 함께 갱신합니다. 테스트를 무력화하거나 실패 조건을 숨기지 않습니다.
- 편집·의존성·포맷·타입·테스트·빌드의 실패 단계를 구분하고 구체적 진단을 제한된 보완 요청에 전달합니다. 실패한 후보는 게시하지 않습니다.

## 6. PR, 교차 리뷰 및 CI

- Issue별 작업 브랜치와 기존 PR을 재사용하며 연결 관계, 대상 저장소·브랜치, HEAD 및 수동 변경을 확인합니다. 응답 유실 시 실제 게시 여부를 조회하고 중복 PR을 만들지 않습니다.
- 리뷰어는 변경된 코드와 관련 테스트를 독립적으로 검토하며 직접 수정하지 않습니다. 승인, 수정 요청, 사람 확인 필요를 구분하고 지적의 근거·위치·영향을 기록합니다.
- 리뷰 결과 형식 교정은 기존 지적이나 수정 요청을 없애고 승인하도록 유도해서는 안 됩니다. 유효한 리뷰 결과를 HEAD와 함께 저장합니다.
- 수정 요청은 같은 PR에서 개발자가 보완하고 새 HEAD에 대해 재리뷰합니다. 권장 자동 수정 한도는 2회입니다. 반복 지적, 변경 없음, 범위 변경 또는 한도 초과는 사람 확인으로 전환합니다.
- 필수 CI는 현재 PR HEAD의 실제 실행·결과와 대응시킵니다. 대기와 실패, 취소, 미확인 상태를 구별하며 이전 HEAD의 성공을 재사용하지 않습니다.
- 확인된 CI 실패는 해당 HEAD의 실패 단계, 파일·줄·오류 등 정제된 진단을 기록합니다. 자동 보완을 지원하는 경우 개발자에게 진단을 전달하고 제한적으로 보완합니다(권장 1회). 새 커밋은 리뷰와 CI를 다시 통과해야 합니다.
- PR에 AI 리뷰 상태를 별도 체크 또는 동등한 방식으로 표시합니다. 리뷰 성공과 CI 대기·실패를 분리하며 상태 표시 실패가 검증 조건을 완화하지 않도록 합니다.
- 댓글 게시 또는 후속 처리 실패 시 저장된 동일 HEAD의 검증 결과를 안전하게 재사용할 수 있습니다. 결과를 확인하지 못한 리뷰는 승인으로 간주하지 않습니다.

## 7. 병렬 개발과 기준 브랜치 변경

- 기준 변경을 감지하고 이전 기준의 검증 결과로 게시하거나 머지하지 않습니다. 자동 복구를 지원하는 경우 게시 전이면 기존 후보를 폐기하고 최신 기준·지침에서 다시 개발합니다(권장 1회). 지원하지 않는 경우 안전하게 중단하고 사유를 기록합니다.
- 게시 후 자동 복구를 지원하는 경우 동일 PR의 작업 브랜치에 최신 기준을 반영합니다(권장 2회). 새 HEAD의 검증·리뷰·CI를 요구합니다.
- 자동 충돌 해소는 확인된 동일 저장소·HEAD의 텍스트 충돌에 한해 명시적으로 허용할 수 있습니다(권장 1회, 최대 10개 파일). 정상 3방향 병합 결과를 보존하고 허용된 충돌 파일만 수정합니다. 삭제·범위 밖 변경·충돌 표식 잔존 등은 거부합니다.
- 브랜치 갱신 응답과 PR 조회 사이의 일시적인 불일치는 예상 커밋과 부모·대상 검증을 거쳐 제한적으로 재조회합니다. 실제 수동 변경이나 예상 밖 HEAD는 중단합니다.
- CI 후속 실행에서도 동일한 복구 경로를 사용하며 예약·횟수를 먼저 기록하여 중복 작업을 방지합니다.
- 개별 복구 한도 외 전체 작업 시간, 호출·비용·재진입 상한을 유지합니다. 자동 복구 과정에서 사용자 중단과 의존성·승인 조건을 재확인합니다.

## 8. 머지 및 종료

- 자동 머지는 사용자가 명시적으로 승인한 자동화 정책의 범위에서만 허용합니다. 기본 대상은 개발 브랜치(dev 등)이며 main 승격·릴리스·배포는 별도 정책을 따릅니다.
- 머지 직전에 승인 라벨·중단·의존성·기준·PR·현재 HEAD·필수 CI 및 독립 리뷰를 다시 확인합니다. GitHub 머지 요청에 검증된 HEAD를 지정하고 브랜치 보호를 우회하지 않습니다.
- 단기 작업 브랜치는 squash merge를 기본으로 하며 장기 브랜치 간 머지는 프로젝트 정책에 따릅니다.
- 머지 후 실제 PR의 대상·머지 커밋을 확인하고 연결 Issue가 completed로 종료됐는지 확인합니다. 종료 요청이 실패하거나 응답이 유실되면 실제 상태를 제한적으로 재조회합니다.
- 이미 머지됐으면 개발·리뷰·머지를 반복하지 않고 남은 종료 단계만 재개합니다. 잘못된 대상, 종료 사유, 불확실한 결과는 사람 확인으로 남깁니다.

## 9. GitHub Actions와 보안

- job별 최소 권한을 명시하고 모델 호출, 상태·댓글 게시, 코드 쓰기, 머지 토큰의 역할을 구분합니다. PR 댓글 쓰기는 pull-requests: write 등 필요한 권한을 실제 토큰으로 확인합니다.
- 자격 증명은 보호된 Environment 등 신뢰된 실행 경계에서만 제공합니다. 후보 코드나 후보 워크플로가 Secret에 접근하지 못하도록 하며 저장소·환경 설정을 검증합니다. 검증할 수 없으면 민감 작업을 진행하지 않습니다.
- 워크플로 편집 허용 시 게시 토큰의 별도 권한과 보호 경계를 검토합니다. 자동화가 자신의 승인·검사·보안 정책을 우회하도록 허용하지 않습니다.
- Issue·PR·리뷰·로그·모델 출력·도구 결과는 신뢰하지 않는 데이터로 취급하며 지침 주입, 명령 실행, 외부 전송, 멘션·마크업 삽입을 방지합니다.
- Actions 버전은 검증된 SHA로 고정하고 실제 존재와 워크플로 간 일관성을 확인합니다. 토큰에 따른 이벤트 발생 제한, 후속 호출 권한, 페이지 조회 및 이벤트 전달을 검증합니다.
- 후속 실행은 관련 브랜치·워크플로·이슈에 한정하고 불필요한 러너 실행을 줄입니다. 이벤트 누락은 실제 상태 대조 및 제한된 재개로 처리합니다.
- API 쓰기 응답이 실패하거나 유실된 경우 성공·실패를 단정하기 전에 실제 상태를 확인합니다. 불확실한 게시를 무조건 재시도하지 않습니다.

## 10. 관측성 및 운영 검증

- 상태 기록에는 규격 버전, Issue·PR·실행 식별자, 기준 및 HEAD, 단계, 현재 상태, 구조화된 실패 코드와 구체적인 사유, 시도 횟수·재개 가능 여부를 포함합니다.
- 모델별 호출 시간과 토큰 사용량, 의존성 준비·캐시·검사 시간, 복구 횟수를 기록합니다. 관측 정보는 코드로 수집하고 확인되지 않은 추정값을 사실로 기록하지 않습니다.
- 실패 사유를 모호한 한 문구로 합치지 않습니다. 공급자 요청 ID, HTTP 상태와 안전한 분류, 검증 단계와 필드·길이·개수 등 필요한 정보만 기록하고 비밀·소스 원문·추론 서명·요청 본문은 노출하지 않습니다.
- 사람 확인이 필요한 중단은 사용자에게 식별 가능하게 알리고 단순 대기·중단·자동화 장애·완료를 구분합니다. 상태 게시 실패도 실제 작업 결과와 구분합니다.
- 상태를 외부에서 읽는 도구는 신뢰된 봇의 구조화 기록과 실제 GitHub 상태를 구분하여 해석합니다. 일반 댓글의 단어만으로 자동화 단계나 완료를 추정하지 않습니다.
- 장애 수정 시 해당 장애를 재현하는 회귀 테스트를 추가합니다. 연결 지연과 본문 지연처럼 서로 다른 실패 조건을 분리하여 불안정한 시간 의존 테스트를 피합니다.
- 모의 API 테스트, 실제 격리 환경 검사, 실제 GitHub Actions·모델 API 종단간 검증을 구별하여 보고합니다. 초기 운영 검증은 작은 승인된 변경으로 진행하며 재개·후속 이벤트·머지·종료를 확인합니다. 실제 운영 검증 없이 성공을 단정하지 않습니다.

## 11. 지침 갱신 및 프로젝트 적용

- 프로젝트별 구현과 이 문서를 비교한 뒤 누락·불일치만 수정합니다. 공통 코드 도입이나 기존 자동화 교체는 필수 요구사항이 아닙니다.
- 프로젝트별 실행 명령, 승인 라벨, 대상 브랜치, 보호 경로, 모델·예산, 상태 대응 관계, 검증 한계를 문서화합니다. 마지막으로 검토한 ai-native 커밋 SHA를 기록하는 것을 권장합니다.
- 새로운 장애가 발생하면 실제 원인과 추정을 구별하여 회귀 테스트를 추가하고 공통으로 적용할 가치가 있는 요구사항을 ai-native의 별도 변경으로 제안합니다.
- 다른 저장소에는 사용자가 요청한 경우에만 변경을 적용합니다. 공통 지침 업데이트 자체가 다른 프로젝트의 변경이나 배포를 승인하지는 않습니다.
